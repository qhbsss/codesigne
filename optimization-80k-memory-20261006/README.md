## 目标与筛选模型

S = 1000 sqrt(30996995 × 1302032 / (TP × TD))。八万分要求 TP×TD≤6306106155.2875；当前乘积10174201282，需要减少38.01866%。TP=250000、TD=25000可以满足预算，但这是预算而非预测。既有P1固定图资源下界193874不能保证实际达到，更不能直接相加不同候选的收益。

每个候选必须满足：硬件菜单和面积≤24mm²、1000周期滑动功耗≤20W、每SM最多4组、每WG私有RF64KiB/分区边界、RF和HBM数据竞争、输入释放STEP.COMMIT、参考数值。RF分区数等于vector_lanes；16路时每分区1024float，8路时2048float且只有8个合法分区，不能沿用RF12..15。HBM通道由地址256B交织，multicast依赖相同issue_begin和64B缓存行；改变屏障也可能改变源读取量。

## 流式权重方案为何值得测试、为何尚不合格

P1提交后仅2个新token。N64输出分工减少读取A的工作组数；K64权重在两套RF0..3/4..7之间轮换，真实MMA后预取下一K面板，RF14累加、RF15输入。前两层只占前16组，使最后一层保留WG16..31的W1及WG32..63的W2缓存。最后一层W1一半流式、一半使用真正保留的权重；W2沿用缓存。模型、稳定softmax、计算输入和K累加顺序均保留。

原始suffix观察器与公共调度器得到相同周期与功耗。独立能量窗口重算误差断言<1e-6W。峰值[18678,19678)与[38866,39866)位于前两层W2，另外[13316,14316)与[33504,34504)位于W1；不是仅第一层初始化问题。8通道饱和HBM动态功耗可到19.2W，加上静态、NoC、RF、计算后超过20W。不能把平均功耗代替窗口峰值。

等待所有前批加载结束能明显降功耗，却扩大关键路径。真实MMA完成的门控保留较多重叠但仍超功耗；前批首个加载完成的门控已是65967cycles，约束合规但不提速。这些依赖均来自实际指令事件。没有候选同时胜过原耗时且满足功耗，因此本轮未新增完整双案例grade，也不发布任何新分数。

## 下一步的实际约束
